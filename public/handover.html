1. Purpose & Overview

This application digitises the SEBI Foreign Portfolio Investor (FPI) Common Application Form (CAF). An applicant chooses whether they are an Individual or a Non-Individual (corporate/entity), fills a multi-step wizard, saves each tab, and submits the application. After submission the form becomes read-only and a printable PDF/preview is available.

The whole feature is implemented in one controller (FpiController), a shared Blade wizard (fpi/index.blade.php) that adapts to the entity type, a start page, and a print/preview view. Data is stored across the normalised CAF schema (41 tables) plus a few JSON columns for the long tail of fields.

3. High-Level Flow

  /  (start page)
   │   choose Individual / Non-Individual  → POST /fpi/start (begin)
   ▼
  /fpi/individual   OR   /fpi/non-individual   (index → renders wizard)
   │   each tab: user fills → "Save Section" → POST /fpi (store)
   │             store() validates that section, writes to DB, marks it complete,
   │             returns JSON {ok, next, message}; the UI advances with no reload.
   ▼
  Final "Declarations" tab saved  →  "Submit Application" enabled
   │   confirmation dialog → POST /fpi/submit (submit)
   ▼
  status = SUBMITTED (read-only)  →  "Print / Preview" → GET /fpi/preview
  • Entity type is chosen once on the start page and stored in the session. The URL (/fpi/individual vs /fpi/non-individual) always reflects it; mismatched URLs auto-redirect.
  • Per-tab AJAX save — nothing is lost between tabs; each save persists just that section and records completion in application_section_progress (drives the green ✓).
  • Draft vs Submitted — a draft applicant row is created on first save; submission flips application_status to SUBMITTED and logs to application_status_history.

Why JSON stores? Many reference-form fields and all the dynamic add-row tables either had no column in the approved schema or depend on master tables that are unseeded (occupation/profession/income codes). Storing them in a section-keyed caf_extra_json document (and beneficial_ownership_json for the BO tables) avoids FK failures and keeps the additive footprint tiny. Genuine scalar homes in the normalised schema are still used wherever they exist.

8. Validation Architecture (3 layers)

Every mandatory field is enforced on three layers that are kept in sync:

  1. Blade asterisk — a red <span class="fpi-req">*</span> on the label (sometimes wrapped in @if($isIndividual) for type-specific rules).
  2. Client-side (JS) — the REQUIRED map (field → label) + conditional blocks inside runRules(). Validation runs on Save/Next (validateStep) and on Submit (validateAll). Invalid fields get .is-invalid and an inline .fpi-invalid-feedback message.
  3. Server-side — sectionRules() in the controller; Individual-only and shared rules. This is the source of truth; the client checks are UX.

Conditional requirements use Laravel's required_if (e.g. PAN number + name required only when hasPan = yes) or custom closures. Added-row tables are validated by the allRowsFilled() closure (server) and a per-container loop (client).

9. Dynamic Tables, Checkbox Groups & Conditional Sections

Repeater tables

Generic add-row tables (Investment Managers, Public Retail, Investor Group, Prior Association, Tax Residencies, Share Classes, Category-I Entities, Clients, Signatories) are built by the JS makeRepeater(cfg) helper. Each registers in REPEATERS, serialises to a hidden <name>Json field on save, and exposes a seed() for auto-fill (window.__seedRepeater(hiddenId, rows)).

Beneficial-Ownership tables

Sub-funds, Intermediate Entities and Controlling Entities use a dedicated module (not the generic repeater), serialised to subFundsJson / intermediatesJson / controllersJson and seeded via window.__seedBo({...}). They persist in beneficial_ownership_json.

Checkbox groups

Multi-select groups (Source of Income .js-income-src, Sensitive Activities .js-sensitive-act, IM Types .js-im-type) can't be serialised by the generic field loop — they are collected into hidden JSON fields in saveSectionAjax() and seeded by autofillExtras().

Conditional show/hide

Driven by the small bindToggle(selectId, targetId, showVal) helper and a few bespoke handlers (hasPAN, custodian, clubbing → investor group, listing, mode "Others", bank-subsidiary, NRI IM sub-options, Reg 5(b)(vii) client eligibility gate, KRA, "same as registered" address).

10. UBO Determination Tool (Non-Individual only)

Step 3 is an interactive ownership-tree builder. The model is entities = [{ id, name, type, owners:[{ id, name, type:'Individual'|'Entity', pct, targetId }] }], rooted at applicant. computePersons() walks the tree, multiplying percentages across layers, to aggregate each natural person's effective ownership %; anyone ≥ 10% (SEBI threshold) is flagged as an identified UBO. The tree serialises to applicants.ubo_structure_json. The identified names feed the Beneficial Ownership tab. The same computation is reproduced in PHP (computeUboPersons()) so the PDF can show the UBO Summary + Ownership Diagram without JS.

Both the UBO Determination tool (Step 3) and Beneficial Ownership (Step 4) are optional when completely empty — the wizard lets the user skip an empty UBO tool silently; Beneficial Ownership must be answered (Yes/No) before submit for Non-Individual.

11. Auto-fill & Save All

The ⚡ Auto-fill & Save All button runs autofillFlow(): for each tab it applies the SAMPLE scalar data (SAMPLE.applicant / SAMPLE.applicantIndividual / per-section), runs autofillExtras() (checkbox groups + __seedRepeater/__seedBo table rows), then saves the tab via AJAX. After all tabs save it asks for explicit confirmation before the final submit (cancel keeps everything saved as a draft). This is a demo/QA convenience — the SAMPLE object is functional dummy data, not stored records.

12. PDF / Print Preview

GET /fpi/preview → fpi/preview.blade.php, a self-contained printable sheet (its own CSS; "Save as PDF" via window.print()). It is entity-aware:

  • Individual — shows the personal-details section; hides the UBO Determination + Beneficial Ownership sections; sections renumber with no gaps.
  • Non-Individual — corporate profile + UBO Determination (tree, UBO Summary, Ownership Diagram) + Beneficial Ownership + everything else.

The header shows the applicant type and the title reads "Application Summary — Individual / Non-Individual FPI". The controller passes decoded JSON stores (financialX, categoryX, depositoryX, additionalX, declX, indX, bo) plus uboPersons, so all captured data is rendered. The "Print / Preview" button appears top-right of the Declarations tab only after submission.

14. How to Extend

Add a simple field to an existing tab

  1. Blade — add the input to the tab panel in index.blade.php (use .fpi-form-group + .fpi-input/.fpi-select; add <span class="fpi-req">*</span> if required).
  2. defaultForm() — add the key with an empty default.
  3. sectionRules() — add its validation rule (and to the JS REQUIRED map if required client-side).
  4. save{Section}Section() — persist it (real column if one exists, else via saveExtra($id, 'section', [...])).
  5. loadForm() — if stored in a real column, read it back (the caf_extra_json slice is merged automatically).
  6. preview.blade.php — add it to the relevant section if it should appear in the PDF.
  7. SAMPLE — add a value so Auto-fill still passes.

Add a new add-row table

  1. Add the container, "+ Add" button, and a hidden <name>Json field in the blade.
  2. makeRepeater({...}) in JS with the column config and section.
  3. Persist in the section's save method via jsonArray($request, '<name>Json') → saveExtra.
  4. Validate rows with allRowsFilled([...]) (server) + a container loop (client) if columns are required.
  5. Seed it in autofillExtras() and render it in the preview.

Add a whole new tab

Add an entry to $steps (both entity branches as needed), a panel with data-panel="<code>", a save<Code>Section() method, rules in sectionRules(), and the code into $order/$orderIndividual and the submit-required list.

16. Database Migrations & Server Move

If the target DB already has the base 41-table CAF schema, only the 3 additive columns are needed. Either run php artisan migrate --force (with the 3 migration files present), or apply the raw SQL:

ALTER TABLE corporate_applicant_details
  ADD COLUMN incorporation_isd_code VARCHAR(5) NULL AFTER incorporation_country_id;

ALTER TABLE applicants
  ADD COLUMN beneficial_ownership_json TEXT NULL AFTER ubo_structure_json;

ALTER TABLE applicants
  ADD COLUMN caf_extra_json TEXT NULL AFTER beneficial_ownership_json;

Also copy the non-DB artefacts: the updated views, FpiController.php, routes/web.php, and public/css/fpi-form.css.

17. Known Gotchas

  • Editor formatter breaks Blade. A JS/Prettier formatter run on .blade.php can mangle -> into - > inside @json(...) in the <script> block, causing a PHP ParseError (500). Fixed by moving those PHP expressions into the top @php block (HTML context). Recommendation: disable format-on-save for Blade files (VS Code: "[blade]": { "editor.formatOnSave": false }).
  • No auth / public uploads — see §4 warning. Address before production.
  • PHP numeric array keys — option lists keyed by '01'..'20' become integers for 10–20; use (string) casts in @selected() comparisons.
  • Checkbox groups & repeaters aren't captured by the generic field loop — they're serialised explicitly into hidden JSON fields before save.
  • The UBO section is optional when empty but mandatory to answer (Yes/No) for Non-Individual before submit.
